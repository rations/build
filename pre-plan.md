# Armvuan pre-plan: Devuan (sysvinit, no systemd) minimal image for Raspberry Pi 5

> Status: **pre-plan**. This file records research and feasibility findings. It will be refined into `plan.md`.
> Scope: private forks `rations/build` and `rations/configng`. Nothing here is meant for upstream Armbian.
> Snapshot: build fork HEAD `4ceded6` (2026-09-25). Line numbers refer to that commit.

---

## 1. Goal and scope

**Today**

- The Pi 5 runs the Armbian Debian **minimal** image.
- XFCE was added afterwards with `armbian-config` → `XFCE01`.
- Development host: **Devuan 6 "excalibur"**.

**Goal**

- A **Devuan excalibur, sysvinit, arm64 minimal image** for the Raspberry Pi 5, built by this build fork.
- The same flow afterwards: install `armbian-config` and run `XFCE01` to get an XFCE desktop without systemd.

**Out of scope for now**

- The full Armbian apt repository, other boards, openrc and runit, and daedalus.
- The design should not rule these out later.

## 2. Short answers

| Question | Answer |
|---|---|
| Can a sysvinit version be built at all? | **Yes.** The Pi 5 kernel (Raspberry Pi fork) and the boot firmware do not depend on the init system. Everything that depends on systemd is userland glue in `build` and `configng`, and all of it can be replaced. Community Devuan images already boot on the Pi 5. |
| Does `deb.devuan.org` carry arm64 like `deb.debian.org`? | **Yes.** `deb.devuan.org/merged` is a full arm64 archive. Devuan's forked packages are merged with every other package passed through from Debian. |
| Which Debian release is excalibur? | excalibur = Devuan 6.x = **Debian 13 trixie**. daedalus = Devuan 5 = bookworm. freia = next testing. ceres = unstable. |
| Can the rest of Armbian be reused? | Yes. Reuse the Pi kernel build (`rpi-6.18.y`), `config.txt` and `cmdline.txt` generation, the BSP scripts, and `armbian-config`. Only the systemd-specific parts need patching. |

## 3. Devuan repository facts

Sources are web research as of 2026-09-25. The sandbox that produced this file could not reach `devuan.org`, so run the commands in §3.1 on the Devuan box before relying on the details.

- **Release file** `http://deb.devuan.org/merged/dists/excalibur/Release`:
  - `Codename: excalibur`, `Version: 6.0` (point release 6.1 on 2026-01-01).
  - `Architectures: all amd64 arm64 armel armhf i386 ppc64el riscv64`.
- **Suites** under `http://deb.devuan.org/merged`: `excalibur`, `excalibur-updates`, `excalibur-security`, `excalibur-backports`, `excalibur-proposed-updates`.
- **Components:** `main contrib non-free non-free-firmware`. Check each suite's `Components:` line. Forum reports show that not every `-security` suite carries `non-free-firmware`.
- **How "merged" works:** it is generated by *amprolla*.
  - Devuan-forked packages (about 400) come from Devuan's pool.
  - Everything else passes through from Debian: the `Filename:` field is rewritten and downloads redirect to Debian mirrors.
  - https://pkgmaster.devuan.org/devuan_mirror_walkthrough.txt
- **Keyring:** `devuan-keyring`, which is **not in Debian**.
  - Provides `/usr/share/keyrings/devuan-archive-keyring.gpg`.
  - Excalibur signing key: `9F8D 6C74 DE66 1075 FD17 1BE3 B398 2868 D104 092C`.
  - Get it from `pkgmaster.devuan.org/devuan/pool/main/d/devuan-keyring/`, or from the Devuan host (`/usr/share/keyrings/`).
- **Bootstrap tooling:**
  - Debian's `debootstrap` is broken for Devuan (Debian bug #1067240: wrong keyring, no excalibur script).
  - **mmdebstrap needs no suite script.** Armbian already uses mmdebstrap, which is a big advantage.
  - Excalibur requires merged /usr, which mmdebstrap does by default.
- **Init and session stack on Devuan:**
  - Init: `sysvinit-core` (default), `sysv-rc`, `orphan-sysvinit-scripts`. `openrc` and `runit-init` are also available.
  - Device manager: `eudev`. On Devuan, `udev` is a transitional package that pulls it in.
  - logind replacement: `elogind` and `libpam-elogind`. `libelogind0` provides `libsystemd0`.
  - polkit: `polkitd` with `libpolkit-gobject-elogind-1-0`.
  - Desktop: Xfce 4.20 is Devuan's default desktop. `task-xfce-desktop` prefers SLiM, but `lightdm` works.

### 3.2 Manual bootstrap smoke test (Phase 0)

This command has not been run yet. It is adapted from existing Devuan Pi builders.

```sh
sudo apt install mmdebstrap qemu-user-static binfmt-support devuan-keyring
sudo mmdebstrap --architectures=arm64 --variant=minbase \
  --keyring=/usr/share/keyrings/devuan-archive-keyring.gpg \
  --include=devuan-keyring,sysvinit-core,eudev,ifupdown,elogind,libpam-elogind \

  "deb http://deb.devuan.org/merged excalibur-security main contrib non-free"
# check: the init binary must be sysvinit, and systemd itself must be absent
tar -tf /tmp/armvuan-rootfs.tar | grep -E '(^|/)(usr/)?lib/systemd/systemd$' || echo "OK: no systemd PID1"
```

## 4. Chosen approach: native Devuan bootstrap in the build framework

Teach the build fork a new **`DISTRIBUTION=Devuan`**, starting with release **`excalibur`**. The rootfs is bootstrapped directly from `deb.devuan.org/merged` with `devuan-keyring`, so **systemd never enters the image**. Everything else the framework does for `BOARD=rpi4b` stays the same:

- kernel build;
- BSP package;
- `/boot/firmware` layout;
- `config.txt` and `cmdline.txt`;
- image assembly.

Where the framework runs `systemctl`, add an init-aware helper so the Debian and Ubuntu paths keep working unchanged. That keeps rebases onto upstream manageable.

**Rejected alternatives, kept for reference:**

- **Convert an Armbian trixie image in place.** Swap the sources to Devuan and install `sysvinit-core`, which is Devuan's documented migration path. It is quick to prototype, but systemd is installed first and removed later, leaving leftovers. The build still runs systemd-only steps before the conversion. It may still be useful as a one-off experiment on the Pi to spot runtime breakage early.
- **Standalone mmdebstrap script** outside the framework, reusing Armbian's kernel and BSP `.deb` files (close to `pyavitz/rpi-img-builder`). It is simpler at first, but it throws away Armbian's image pipeline and the ability to follow upstream.

### Phase 2: BSP, first boot, and Pi specifics
- Add `/etc/init.d/armbian-*` scripts and `unblock-rfkill`, and make the BSP postinst init-aware.
- Patch `armbian-firstrun`, `armbian-resize-filesystem`, `armbian-ramlog`, `armbian-zram-config`, `armbian-truncate-logs` and `armbian-common`.
- Patch `armbian-firstlogin`: ssh restart, timezone, network, DM.
- Add the Devuan branch in `bcm2711.conf`. Never install `raspberrypi-sys-mods`.
- **Done when**, on the Pi 5:
  - the image boots to a console login on HDMI and on serial;
  - the root filesystem is resized;
  - the first-login wizard completes;
  - Ethernet gets DHCP and SSH works;
  - `cat /proc/1/comm` prints `init`.

### Phase 3: `configng` on sysvinit
- Add the sysvinit backend in `module_service.sh`.
- Add Devuan→Debian codename mapping in `module_env_init.sh` and `parse_desktop_yaml.py`.
- Adapt the networking and DM/autologin paths in `module_desktops.sh`.
- Drop `systemd` from the `.deb` Depends.
- Build `armbian-config` locally, and either install it from a local repo or point `extensions/armbian-config.sh` at the fork.
- **Done when:** `armbian-config --cmd XFCE01` on the Phase 2 image installs XFCE, starts lightdm, autologin works after a reboot, NetworkManager manages the network, and systemd is still not installed.

## 7. Prior art to study

- **`amateur80lvl/armvuan`** (https://github.com/amateur80lvl/armvuan). A Devuan fork of Armbian that uses **this same name**.
  - It targets daedalus, uses the `./compile.sh armvuan-build … RELEASE=daedalus` command, and converted only `armbian-ramlog` and `armbian-hardware-optimization` to sysvinit.
  - Read it for its patches.
  - **Name clash:** pick a different name, or accept the overlap, before publishing anything.
- **`pyavitz/rpi-img-builder`.** Already builds Devuan excalibur images for the Pi 5 (bcm2712) with mmdebstrap and ifupdown or NetworkManager. It is a good reference for the package lists and the boot partition layout.
- **`arm-files.devuan.org`**, "RaspberryPi Latest Builds". Unofficial Devuan 6.x images for the Pi 2 through Pi 5, useful as known-good references.
- **`emojifreak/debian-rpi-image-script`** (`devuan-rpi-sd-builder.sh`). An older mmdebstrap-based Devuan Pi builder. Its diff against the Debian builder is essentially `--include=sysvinit-core,eudev,devuan-keyring` in place of `systemd-sysv,udev,debian-archive-keyring`.
- Armbian forum threads "Devuan Armbian?", "Replace systemd with sysvinit" and "Armbian Devuan Based?". They confirm there is no upstream support and that swapping the init system breaks parts of `armbian-config`, which §5.2 covers.

## 8. Risks and open questions

1. **Upstream drift.** Both forks will need regular rebases onto Armbian. To keep rebases cheap:
   - put Devuan logic in `extensions/devuan.sh` and new files;
   - keep core edits small and grouped behind `DISTRIBUTION == Devuan`;
   - wrap them in helper functions.
2. **Package availability on Devuan arm64** has not been verified from this environment: `netplan.io`, `profile-sync-daemon`, `slick-greeter`, `pipewire` + `wireplumber` without a systemd user session. Phase 0 settles this.
3. **Audio under sysvinit.** Without a systemd user session, PipeWire and WirePlumber must be started from the XDG autostart entries, or the Devuan `pipewire` autostart. The fallback is PulseAudio.
4. **Display manager.** Keep `lightdm` + `slick-greeter`, which matches Armbian, or use Devuan's default SLiM. The recommendation is lightdm. Check that its `/etc/init.d/lightdm` script and `/etc/X11/default-display-manager` behave as expected.
5. **Pi 5 kernel page size.** Armbian boots `vmlinuz` (4K pages) through `kernel=vmlinuz`. Keep it, so jemalloc and other software that breaks on 16K pages is unaffected.
6. **Keyring distribution.** The vendored `devuan-archive-keyring.gpg` needs updating when Devuan rotates keys (each release).
7. **Armbian apt repo.** It is disabled (`SKIP_ARMBIAN_REPO=yes`), so kernel and BSP updates on installed systems need a private apt repo, or manually built `.deb` files. Decide this in `plan.md`.
8. **Future options.** openrc or runit support, and daedalus images. The Phase 1 helper (`chroot_sdcard_enable_service`) should use an `INIT_SYSTEM` variable, not a hard-coded sysvinit, so these can be added later.
